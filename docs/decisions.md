# Decisions

**Read this when** you need to know why something is the way it is, or before reversing a choice.
**Related:** [open-questions.md](./open-questions.md) for what isn't decided yet.

---

## How to add or change a decision

1. **Add a row.** Use the next ID in the right group, with the date and who decided.
2. **Never delete a decision.** If a new one reverses an old one, mark the old row *Replaced by Xn* and keep it.
3. **Update the docs.** In the same change, update every doc the decision affects (the "Docs" column), and the summary in [README.md](./README.md#key-decisions) if it's a key decision.
4. **Close the question.** If the decision answers a question in [open-questions.md](./open-questions.md), mark that question answered and link here.

**Groups**

- **D:** taken by the founders.
- **B:** the basics both earlier plans agreed on.
- **P:** proposed by the AI assistant when writing this plan, and accepted with it. P decisions are the easiest to revisit.

## Proposed while building Foundations (18 Nov 2026)

| ID | Decision | Why | Docs |
|---|---|---|---|
| P24 | Each endpoint is defined once in `shared/` (`defineEndpoint`) with its schemas, session need, permission and AI tier. The backend won't start if one has no implementation, and the type check fails if a permission has no rule | One definition feeds validation, the typed client, OpenAPI and the checks; a forgotten rule can't ship | [api.md](./api.md#adding-an-endpoint) |
| P25 | Session, AI-tier and permission checks run before the input is validated | Callers who may not use an endpoint learn nothing about it | [architecture.md](./architecture.md#api) |
| P26 | Tests use Vitest against a real PostgreSQL; each test file gets its own copy of a migrated template database | Tests see the real triggers and constraints, and stay fast and independent | [architecture.md](./architecture.md#stack) |
| P27 | Two COAL lint rules keep the parts apart (`coal/part-boundaries`) and stop modules using each other's tables (`coal/module-tables`); another stops website text being written into components | The architecture rules are checked on every change, not just reviewed | [architecture.md](./architecture.md#growing-to-all-of-jayon) |
| P28 | Insert-only tables are guarded by a database trigger. Audit entries are written at the end of each change's transaction, under a short lock, so the hash chain has one order | The guarantee holds whatever code runs; the lock is held only briefly | [data-model.md](./data-model.md#conventions) |
| P29 | Files are uploaded straight to a staging area in storage through short-lived links that accept only the declared size. On completion, COAL reads the staged file once, records its size and hash, and copies exactly those bytes (checked by ETag) to a key no upload link can write to. The content type comes from the file extension | Large files don't pass through the API, nothing trusts the browser's word, and a recorded hash always matches the served file, as signatures need | [api.md](./api.md#documents-templates-files-and-sources) |
| P30 | `users.product_line_id` is the one platform table pointing at a department table, until the org chart replaces it | Sign-up needs a Lead's product line now; the org chart is the proper home later | [data-model.md](./data-model.md#conventions) |
| P31 | Local file storage uses the `pgsty/minio` community build, and the backend creates its bucket on start in local work | MinIO stopped publishing its own images | [architecture.md](./architecture.md#environments-and-hosting) |
| P32 | An `Idempotency-Key` is claimed before the action runs; a retry that arrives meanwhile is refused, and a failed request releases its key | A retry during a slow first request must not repeat the action | [api.md](./api.md#conventions) |
| P33 | The backend trusts no proxy's `X-Forwarded-For` unless named in `TRUST_PROXY`, and only a reverse proxy that overwrites that header may be named. The website's rewrite never is | A trusted header that clients can set would let anyone skip the sign-in rate limit; a shared counter is the safer fallback | [architecture.md](./architecture.md#security-basics) |

## Proposed while building documents and signing (19 Nov 2026)

| ID | Decision | Why | Docs |
|---|---|---|---|
| P43 | A template lives in COAL (Word file in storage, specification in the database), not in the repository. A new version is **checked** when it is added (a real Word file under 10 MB, a clean virus scan when a scanner is set up, placeholders that match the specification both ways, a sample PDF that renders) and is saved as a **draft**. **Activating** is a separate step by the VP or the R&D Head, who may activate their own upload ⚠ (S6, S9). Documents keep the version they were made from | The VP or Head can add a new form without a release, a bad file can never replace a good one, and old documents stay reproducible | [documents-and-signing.md](./documents-and-signing.md#adding-a-template) |
| P44 | A new version of a template needs only the Word file: it reuses the previous version's specification. A first template, or a change to the specification (new fields, new sections), is prepared with the AI coding assistant from Jayon's sample documents and loaded with the import command | The people who upload forms shouldn't have to write YAML, and a specification change needs a developer's eye on the document type | [documents-and-signing.md](./documents-and-signing.md#adding-a-template) |
| P45 | COAL ships **made-up sample templates** for every document type that uses a template, loaded into the dev database when the backend starts and by `templates:import --samples`. | P46 | A template's placeholders are flat names. A field is `{name}`, a written section is `{section_id}`, and a table is a loop `{#members}{name}{role}{/members}`. Fields from records are filled afresh at every save, never typed and never written by the AI; the person's own fields and the written sections come from what was typed, and anything not sent keeps the previous version's text. The PDF is made while saving (docxtemplater, then Gotenberg), so a version never exists without its PDF; if the PDF service is down the save fails and nothing is saved | One place decides what a document says, and a signature can always point at a PDF | [documents-and-signing.md](./documents-and-signing.md#how-documents-are-filled) |
| P47 | A saved version never changes: a database trigger refuses changes to its content, files and hashes, refuses deletes, and lets an approved version only be superseded. Its hash is the SHA-256 of its content (canonical JSON, or the uploaded file's bytes) and of its PDF. Saving what is already saved makes no new version. A version with the signers can't be edited; after a return the authors save a new version. The revision letter (A, B…) is given at approval | The record of what was signed can't be rewritten, even by a bug | [documents-and-signing.md](./documents-and-signing.md#versions-and-revisions) |
| P48 | A version is signed in rows. **Prepared** is signed by the click that submits it. **Reviewed** is signed by anyone with one of the template's `reviewed_by` roles ⚠ (S1). **Approved** is signed by the step's signer, or the roles the template names, and by every Board member at a step the whole Board must sign. A person can't sign Approved on a version they prepared. A row nobody can sign (Approved on a step with no sign-off, such as 2a) is left out, and the author's signature is then the last. A return cancels the other rows | Rows follow the route and the template, and the same person can't be both the author and the approver | [documents-and-signing.md](./documents-and-signing.md#signature-rows) |
| P49 | The **step sign-off record** is a document of type `STEP_SIGNOFF` that COAL makes when a step with a sign-off is submitted, a new version each time. The submitter signs Prepared; the signer signs Approved *by approving the step*, never on the record alone. Returning the step returns the record. Submitting a step does not require its documents to be approved: the preview warns, and the record lists each output with its status and hash ⚠ (S7) | The signer signs something concrete, including steps with no named document, and the route isn't blocked by a document that is still being reviewed | [documents-and-signing.md](./documents-and-signing.md#step-sign-off-records) |
| P50 | When a send-back resets a step, the latest version of each of its documents is copied into the new iteration as a new draft (same content and PDF, marked carried forward). A version still with its signers is returned first. Sign-off records are not copied: a new one is made when the step is submitted again | People revise rather than start again, and what was signed stays as it was | [workflow.md](./workflow.md#failure-and-rework) |
| P51 | Every decision (Go, checkpoint, the step-12 answers, hold, resume, drop) is signed by the person who made it, with a hash of exactly what was decided. Send-backs are recorded and audited but not signed | The decisions the documents name are signed; a send-back's reason is already kept in the record | [documents-and-signing.md](./documents-and-signing.md#signature-rows) |
| P52 | Document access is need-to-know, decided by one pure rule in the permission module: the VP and the Head see all; a Lead sees their product line's; the team sees their project's; the Board sees checkpoint papers; the Lead sees only the outcome of Board papers; a **budget annex** is a separate document type that only the Board, VP, Head, the Lead of the line and R&D Ops on the project see; anyone asked to sign a version can read it. Drafts are for the people who work on the project, and a document with only drafts isn't listed for anyone else. The signed-in person is told who can open something, never what it contains | Matches the need-to-know table in `roles-and-access.md`; sharing a plan without its budget is possible | [roles-and-access.md](./roles-and-access.md#content-is-need-to-know) |
| P53 | A file opens for the person who uploaded it and for anyone who may see a record that holds it: a document version's PDF or upload, an attachment or source, a template's sample (and its Word file for the VP and Head). Attachments and sources belong to a project and to exactly one step, document or task. People on the project add them; reading follows the step's or the document's rule, and the Board sees step attachments only at checkpoints | Evidence shared on a record should be readable by the people who can read the record, and by no one else | [roles-and-access.md](./roles-and-access.md#content-is-need-to-know) |
| P54 | Virus scanning uses ClamAV, which is optional locally and required in production (`CLAMAV_HOST`). An upload is scanned when it is completed; a scanner that can't be reached leaves it "not scanned", and a sweep every minute tries again. Where a scanner is set up, an unscanned file can't be opened, and an infected one can't be opened or used anywhere. Where none is, uploads open as before, which is fine only while COAL holds made-up data | Uploads are scanned before anyone opens them (I9) without making ClamAV a requirement for local work | [documents-and-signing.md](./documents-and-signing.md#files-pictures-and-sources) |

The Lead proposes a change by recording a deviation with a new date ⚠ (W13) | The baseline is kept for measuring, every change is recorded, and the launch date needs the VP | [dashboard.md](./dashboard.md#where-dates-come-from), [roles-and-access.md](./roles-and-access.md#what-people-can-do) |
| P58 | The forecast follows the route: an open step ends at its start plus its length (the baseline's, where there is one), moved later by the latest new date on the step's open work (a person's new date from a deviation, which also moves their task's due date) and never into the past; a waiting step starts when its inputs are expected to end. The forecast launch is the expected end of step 25. The planned launch is set at Go from the default lengths and then follows the baseline | The forecast needs no guessing and reacts at once to a late input | [dashboard.md](./dashboard.md#where-dates-come-from) |
| P59 | Health follows the plan's thresholds, kept as settings (`settings` table, `schedule` key, defaults in `shared/`). Every step's dates and health and the project's are stored, and worked out again after every action, date change and deviation, and every night at 00:10 Indian time, because time passing makes steps late | Widgets read stored values, and a step turns overdue without anyone acting | [dashboard.md](./dashboard.md#health) |
| P60 | A **deviation** is insert-only. Its recorder is the task's assignee, the Lead of the line or the Head. A late step can't be submitted until someone has given a new date that hasn't passed yet, and a late task can't be closed until a deviation explains the date it missed (`DEVIATION_REQUIRED`): an earlier explanation doesn't cover a new miss, and the system's "rework" records explain nothing. The new date moves the task's due date (not its first) and the forecast. The next role up the ladder, or anyone above, in the project's scope (never the recorder) confirms it or corrects it: a correction is a new deviation that points at the old one, and a review row records which | A late task always has a reason on record, and an explanation can be corrected but never rewritten | [dashboard.md](./dashboard.md#deadlines-alerts-and-deviations) |
| P61 | Who sees a deviation's cause by name: the VP and the Head; a Lead for the people below them in their line; the person named; and the person who recorded it. Everyone else sees the role (or "an outside party") and the category. The sentence of explanation and the comments are content, shown only to people in the project's scope | Matches the need-to-know table; a delay is status, who caused it is not | [roles-and-access.md](./roles-and-access.md#content-is-need-to-know) |
| P62 | Notifications are in-app for now. Subscribers of the event outbox write them: a task assigned, a signature asked for, work returned, a checkpoint decided, a project held, resumed or dropped, and a deviation to review or naming someone. Each is written from the route's work-message template, once per person and event, and a queued task tells everyone who can claim it. Messages never carry comments or reasons. @mentions wait for comments on steps | The route owns the words, a retried event can't repeat a message, and content stays in COAL | [dashboard.md](./dashboard.md#notifications-and-work-messages) |
| P63 | Reminders and escalation run each working day at 08:30 Indian time, from the thresholds in settings. A VP's or the Board's overdue signature is not escalated above them: the people who asked are told. The "weekly exception list" is, for now, one notification to the Head and the VP when a task passes 5 working days late, plus the Delays widget | Every rule in the plan is built; a weekly digest can follow with email | [dashboard.md](./dashboard.md#deadlines-alerts-and-deviations) |
| P64 | Live updates are hints, never content. The outbox subscriber tells PostgreSQL (`NOTIFY coal_live`) which widgets changed or who has a new notification; each API copy listens (when its first client connects) and passes hints to its open `GET /api/v1/stream` connections. The website then fetches through the normal, permission-checked API | Several backend copies work without a message broker, and a hint can't leak anything | [architecture.md](./architecture.md#events-and-live-updates) |
| P65 | Widgets are defined in `shared/` and return one generic shape (counts, and rows with a title, a subtitle, badges, values for the table's columns, actions and references), so the website and the later mobile app draw every widget the same way. Each counts only what the viewer may see. Team workload and measures for "people below" follow the ladder; a Lead's people are those on their product line's projects; the Board sees department totals | New departments add widgets without new screens | [dashboard.md](./dashboard.md#widgets) |
| P66 | Measures are worked out live from tasks, deviations and documents. The on-time rate counts finished work tasks by their **first** due date over 90 days, stopping the clock when the doers hand the step in (not when the signer signs), and leaves signatures to the sign-off turnaround. Rework is the share of a person's submitted document versions that were returned | They work from day one, and the numbers can be recomputed from the record | [dashboard.md](./dashboard.md#measures) |
| P67 | Lists that page by cursor compare and order by the timestamp cut to milliseconds. A cursor carries a JavaScript date, which keeps only milliseconds, while rows made in one transaction share one microsecond time: the old comparison skipped the rows that followed a page's last row. This changed the activity feed and the task, project, deviation and notification lists | Found while adding events to every action; no list may lose rows between pages | [api.md](./api.md#conventions) |
| P68 | Time is read from one place (`deps.now`), so due dates, reminders, task stamps and tests agree on "today", and tests move the clock instead of waiting | Lateness is the heart of this block, and it has to be testable | [architecture.md](./architecture.md#background-jobs) |
| P69 | When a step with a signer is submitted, its doers' tasks become **waiting**, and a return opens them again. A waiting task is not late and gets no reminders: the signature has its own due date and reminders. A send-back's reset reopens the step and makes new tasks, so nothing waits on a step that has restarted | Otherwise a doer who has handed in the work would be marked late while the Board takes its time | [dashboard.md](./dashboard.md#widgets) |

## Proposed while building the Workstation and AI (20 Nov 2026)

| ID | Decision | Why | Docs |
|---|---|---|---|
| P70 | Block 5 is built in five parts: groundwork (tasks given by hand, proposals, search), the AI gateway and chat, the Workstation page, the writing features, then safety and the test sets. The AI's known-answer tests (`pnpm eval:ai`) are run by hand, not in CI; the automatic tests use a scripted stand-in for the model | Each part can be tested and committed on its own; the evaluation needs a key and costs money | [roadmap.md](./roadmap.md#build-order), [workstation-and-ai.md](./workstation-and-ai.md#testing-the-ai) |
| P71 | One endpoint, `POST /tasks`, makes own tasks, assignments and requests. The person says who it is for; one pure rule (`howToGive`) decides from the ladder whether it is assigned (`work`) or asked (`request`), and `?preview=true` says which. Its tier is `auto`, but a "via AI" call may only make the user's own task: work for anyone else goes on an action card | The person can't pick the wrong one, and the AI can't assign work without a confirmation | [roles-and-access.md](./roles-and-access.md#assigning-work-and-making-requests), [api.md](./api.md#tasks-and-requests) |
| P72 | Work given by hand belongs to no run step: no step closes, resets or waits on it, it gets no reminders, and a late one can be closed without a deviation ⚠ (W25). Its events carry no project, so the project's activity feed, which shows status to everyone, never shows its words. A request is accepted explicitly or by starting it; a decline needs a reason, which the person who asked sees on the task but not in the notification | The route's plan and measures stay about the route; the words of a request are content | [api.md](./api.md#tasks-and-requests), [dashboard.md](./dashboard.md#deadlines-alerts-and-deviations) |
| P73 | A proposal's action is a call to an existing endpoint (`endpoint`, `params`, `query`, `body`), run through that endpoint's own checks and handler as the user. Only `auto` and `confirm` endpoints whose implementation can describe itself may be proposed. The preview runs every action in order in one transaction and rolls it back, writing no files and making no PDFs; confirming runs them again for real and compares, saving a new version and answering `PREVIEW_CHANGED` if anything differs. Proposals expire after 72 hours ⚠ (AI9) | Cards can't drift from what the screens do, a bundle's preview includes how its actions affect each other, and a card never does something other than what it showed | [api.md](./api.md#proposals-and-action-cards) |
| P74 | Search is PostgreSQL full-text search (English stemming, with parts of codes and names matched too), across projects, documents, tasks and people. Each kind is filtered by its own rule: every project, documents the person may open in full (drafts only for the people who work on the project; a document they may know only the outcome of is left out, so its words can't be found), their own tasks, queue and given work, and the directory | Search must never reveal what a person couldn't open; vector search can come later without changing the endpoint | [api.md](./api.md#dashboard-and-notifications), [architecture.md](./architecture.md#ai-module) |
| P75 | The AI's tools are thin wrappers over endpoints, run through one function (`callEndpoint`) that every action card also uses: the endpoint's own input checks, session, AI tier, permission and handler, as the person, marked "via AI". Tools exist only for `read` and `auto` endpoints (a test fails otherwise, and fails if the card catalogue offers a `never` endpoint). A refusal or failure goes back to the model as text, with who can help, never as a crash | What the AI can do is exactly what the endpoint allows, so a new endpoint can't quietly give it new powers, and the model can explain a refusal | [workstation-and-ai.md](./workstation-and-ai.md#the-tools), [architecture.md](./architecture.md#ai-module) |
| P76 | A provider adapter runs one turn and returns words and token counts: Anthropic through the Vercel AI SDK (the key's workspace named on every call), the Copilot SDK as a development-only stand-in (D19), and a scripted one for tests. A session lasts one turn; the conversation comes from COAL's own database. The Copilot adapter offers only COAL's tools (`custom:*`), refuses every permission request, is a dev dependency, and the backend refuses to start with it in production | The provider can change without touching the rest, and the stand-in can't reach a shell, files or the web | [workstation-and-ai.md](./workstation-and-ai.md#ai-providers) |
| P77 | Facts are cited by source tags. Each tool result tags the records it read (`[S1]`, `[S2]`…); when a reply is saved, tags that match a record read in that reply become citations (type, label, link, passage) and any other tag is removed | "Facts come from records" is checked by the server, not only asked of the model | [workstation-and-ai.md](./workstation-and-ai.md#citations) |
| P78 | The AI's cost is worked out from token counts at starting prices by model family ⚠ (AI11). Each person's day (Indian time) has a budget (D18) that is checked before each message; a reply may use at most 20 tools and 2 minutes. Cached tokens count as ordinary input, so the budget errs on the safe side | One rule works for every provider, including the stand-in, which reports no dollars | [workstation-and-ai.md](./workstation-and-ai.md#what-is-logged) |
| P79 | One `ai_requests` row is written for each reply (and one for a new chat's title), and one `ai_tool_calls` row for each tool, both insert-only. Logs hold no words from the person or the AI: those are only in the chat, which only its owner can read, whatever their role. Which questions to keep or delete is open ⚠ (AI12) | An audit of what the AI did and cost, without a second copy of private content | [data-model.md](./data-model.md#ai-and-proposals) |
| P80 | One reply is written at a time per chat. The same endpoint takes the message and streams the reply when the request asks for `text/event-stream`, and returns the finished reply as JSON otherwise (so WhatsApp and tests need no stream). Closing the connection stops the reply, and a stop request reaches the API copy that is writing it ⚠ | Refusals (budget, busy chat) come back as ordinary problem responses before a stream starts; stopping across several copies needs a message between them, left for when there are several | [api.md](./api.md#ai) |
| P81 | The instructions are layers in files (platform rules, company and the route read from the route definition, the person's role from the route, the person, what the chat is pinned to, and the action cards still waiting), and every request logs a prompt version that is a fingerprint of the fixed text. The AI writes plain text (no Markdown, no links) and puts everything in one request on one card, and may change a waiting card (`revise_card`) but never confirm or discard it | A change of behaviour can be traced to a change of words, and the Workstation shows only text, citations and cards | [workstation-and-ai.md](./workstation-and-ai.md#how-the-ai-is-told-what-to-do) |
| P82 | The Workstation is one page whose address says what is open: `?chat=` for an existing chat, or `?project=&step=&document=&task=&widget=` for what a new chat is about, so every "Ask AI" and "Open in Workstation" is a link and a chat is only made when the first message is sent. The reply is read from the event stream with `fetch` (a message is a POST), and the saved chat is fetched again when it ends, so the page shows what was stored | No empty chats, links that work from anywhere, and what is on screen is what is saved | [workstation-and-ai.md](./workstation-and-ai.md#the-workstation) |
| P83 | Citations are numbered 1, 2, 3 in the order the saved answer first uses them, whatever tags the AI saw while it read. A citation's id is a string, since a Dashboard widget is cited by its key | A reader sees a tidy list; found when the chat page first read an answer that cited a widget | [workstation-and-ai.md](./workstation-and-ai.md#citations) |
| P84 | A card of tasks is edited on screen; any other card is changed by asking the assistant, which is told which cards wait and can change one (`revise_card`) but never confirm it. `/` commands are starters for a message, not new powers | Editing every kind of action on a form would need a form for each; the server checks the changed card again either way | [workstation-and-ai.md](./workstation-and-ai.md#the-workstation) |
| P85 | A sample document becomes a template by COAL's code editing the person's own Word file (for a text PDF, building a plain Word form): the AI decides what each numbered part is (boilerplate, field, written section) and the specification; code inserts the placeholders, keeping the layout, and runs the same checks as an upload. The AI never writes the file, and a failed check goes back to it as text | The AI is good at deciding what a part means and poor at being exact; the checks that protect a template already exist and shouldn't be bypassed | [workstation-and-ai.md](./workstation-and-ai.md#making-a-template-from-a-sample-document) |
| P86 | `POST /templates` moves from AI tier `none` to `confirm`, so a card may carry it; a new `POST /document-types` (VP and R&D Head, `confirm`) lets the same card add a type that doesn't exist yet. The two actions run in one transaction, so a failure leaves neither | The route has documents whose type isn't seeded yet, so a sample often needs a new type; a person confirms once | [workstation-and-ai.md](./workstation-and-ai.md#making-a-template-from-a-sample-document) |
| P87 | A template made through the chat is saved as a **draft**; making it active stays a separate act by the VP or the R&D Head on the Templates page. The card's Edit changes only what leaves placeholders where they are (name, steps, notes, roles, section titles, instructions, required, a field's source); anything else is done by asking, which builds again | Activation changes what every new document looks like; a placeholder moved by hand-editing a form could break the file | [workstation-and-ai.md](./workstation-and-ai.md#making-a-template-from-a-sample-document) |

A template record keeps the sample file it was made from | Samples come from outside the AI's control and could hold hidden instructions; keeping the source lets a person redo or audit a template | [workstation-and-ai.md](./workstation-and-ai.md#safety-basics) |
| P89 | Text PDFs are accepted as samples next to Word files, up to 30 pages and 10 MB, and read in-process with a time limit. Scans and photos are refused until a reader for them exists. A template from a PDF has a plain layout, and the card says so. Chats that hold a sample file run on a new `template` model purpose (`AI_MODEL_TEMPLATE`, Sonnet by default, never the cheap model), so changing the everyday chat model later doesn't weaken it | A PDF carries no layout to keep and reading it is an extra attack surface, so the limits and the plain label keep it honest; this is the hardest thing the AI is asked to do, so it gets the strongest default | [workstation-and-ai.md](./workstation-and-ai.md#making-a-template-from-a-sample-document) |

A PDF is first turned into a plain Word file with the same numbering, so one editing path serves both | The AI decides what a part is; exact edits and consistent checks are code's job. Gaps are reported, not refused. Nothing is submitted or signed | "Facts come from records" is enforced where the write happens, not only asked for. The database refuses changes to all three | Marks must be true: they come from comparing text, not from asking the AI.
